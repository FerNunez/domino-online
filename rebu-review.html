The 3 Communication Channels

⚡

Synchronous — gRPC

Used when the caller needs a response immediately. Browser → gateway → trip-service / driver-service. Strong typing via .proto, request-response semantics.

PreviewTrip · CreateTrip · RegisterDriver
📨

Asynchronous — RabbitMQ

Used when decoupling matters and no immediate response is needed. Single topic exchange named trip. Publisher never knows about consumers — add subscribers with zero changes to publishers.

topic exchange · routing keys · DLQ
🔌

Real-time — WebSocket

Push notifications to browsers. Gateway maintains two hubs: /ws/drivers and /ws/riders. Bridges RabbitMQ → WebSocket using the OwnerID field in every AMQP message.

ConnectionManager · OwnerID routing

The 30-Step Ride Lifecycle

Every successful ride touches all 5 services. Each step maps to specific code.

Phase 1 — Preview (steps 1–6)

01Browser Rider opens app → WebSocket connects to /ws/riders?userID=<uuid>
02Browser Rider clicks destination → POST /trip/preview
03gateway Receives request → gRPC PreviewTrip → trip-service
04trip-svc HTTP → OSRM → get driving route & distance
05trip-svc Calculates fares for SUV / sedan / van / luxury → saves preview to MongoDB
06trip-svc Returns route + 4 fare options → gateway → 201 to browser

Phase 2 — Trip Creation (steps 7–10)

07Browser Rider selects fare → POST /trip/start
08gateway gRPC CreateTrip → trip-service
09trip-svc Validates fare → creates TripModel (status: pending) in MongoDB
10trip-svc Publishes trip.event.created → RabbitMQ

Phase 3 — Driver Matching (steps 11–14)

11driver-svc Consumes trip.event.created from find_available_drivers queue
12driver-svc Picks random matching driver → publishes triver.cmd.trip_request
13gateway Consumes triver.cmd.trip_request → reads OwnerID = driverID
14Browser Gateway → WebSocket → driver's browser (trip request arrives)

Phase 4 — Driver Acceptance (steps 15–20)

15Browser Driver accepts → sends driver.cmd.trip_accept over WebSocket
16gateway Receives WS message → publishes triver.cmd.trip_accepted to RabbitMQ
17trip-svc Consumes triver.cmd.trip_accepted from driver_trip_response queue
18trip-svc Updates trip status = accepted, stores driver info in MongoDB
19trip-svc Publishes trip.event.driver_assigned
20trip-svc Publishes payment.cmd.create_session

Phase 5 — Payment (steps 21–30)

21payment Consumes payment.cmd.create_session
22payment → Stripe API → creates Checkout Session
23payment Publishes payment.event.session_created (with Stripe session ID)
24gateway Consumes payment.event.session_created → reads OwnerID = userID
25Browser Gateway → WebSocket → rider's browser (Stripe session ID delivered)
26Browser Rider's browser redirects to Stripe Checkout → rider pays
27Stripe Stripe → POST /webhook/stripe on api-gateway
28gateway Verifies Stripe HMAC signature → publishes payment.event.success
29trip-svc Consumes payment.event.success
30trip-svc Updates trip status = payed in MongoDB ✓

Failure Paths

⚠️
No drivers available driver-service finds 0 matching drivers → publishes trip.event.no_drivers_found → gateway forwards to rider's WebSocket → UI shows error.
⚠️
Driver declines Driver sends driver.cmd.trip_decline → trip-service re-publishes trip.event.drivers_not_interested → re-enters find_available_drivers queue → driver-service picks a different driver. Automatic retry loop.

Chapter-by-Chapter Review

The key learning from each chapter, distilled.

CH01 What We Are Building ✓ done

Established the mental model: a ride-sharing system with 5 services, 3 communication channels, and a 30-step ride lifecycle. Why microservices? Each service has its own bounded context, external dependency, and reason to change.

The lens: Before writing code, you mapped who talks to whom and why. gRPC = needs answer now. RabbitMQ = fire and forget. WebSocket = persistent push.
CH02 Repo Layout — Single Go Module Monorepo ✓ done

All services live under one go.mod with module path rebu. No replace directives, no Go workspaces needed. Shared code under shared/ is imported with simple paths like rebu/shared/messaging.

Why one module? Eliminates version coordination between services. All services always use the same shared library version. In a real team you'd split modules — here, one module keeps focus on the distributed system patterns, not the toolchain.
CH03 Shared Foundations — Contracts, Env, Retry ✓ done

Built the shared plumbing: AmqpMessage envelope, WSMessage for WebSocket, APIResponse wrapper, routing key constants, and env.GetString with defaults.

The envelope insight: AmqpMessage.OwnerID is the routing key for WebSocket delivery. The publisher doesn't know anything about WebSockets — it just sets a string. The gateway reads it and routes. Clean decoupling across two completely different protocols.
CH04 Protobuf and gRPC — Typed Contracts ✓ done

Defined trip.proto and driver.proto. Generated Go stubs into shared/proto/. Wired gRPC clients in services/api-gateway/grpc_clients/. Learned that only the gateway makes gRPC calls — internal services never call each other directly.

Why gRPC over REST for internals: The .proto file is a compiler-checked contract. A rename or type change is a compile error, not a runtime crash at 3am. Also adds trace propagation for free via otelgrpc interceptors.
CH05 Async Messaging — RabbitMQ Topic Exchange ✓ done

Built shared/messaging/rabbitmq.go. One topic exchange named trip. All topology declared idempotently in NewRabbitMQ(). Prefetch=1 + manual ack. Retry with exponential backoff before DLQ.

The topology insight: Every service re-declares all exchanges and queues on connect. AMQP declarations are idempotent — no "who creates the queue first?" race condition. Whoever connects last wins nothing special.
CH06 Distributed Tracing — OpenTelemetry + Jaeger ✓ done

Added shared/tracing/. One InitTracer() call in every service's main.go. TracedPublisher injects traceparent into AMQP headers. TracedConsumer extracts it. One trace ID covers the full ride across all 5 services.

The propagation chain: HTTP header → gRPC metadata → AMQP message header → gRPC → HTTP. The same trace ID flows through all three protocols automatically, giving you a single Jaeger trace showing the entire 30-step ride.
CH07 Trip Service — System of Record ✓ done

Full Clean Architecture: domain/ → service/ → infrastructure/. Service layer depends on interfaces (repo, publisher). MongoDB in infra, in-memory repo for tests. Consumes AMQP, exposes gRPC, calls OSRM for routing.

The dependency direction: infra → service → domain. The domain never imports infrastructure. The service layer knows about interfaces, not concrete drivers. Swap MongoDB for Postgres by changing only infrastructure/repository/.
CH08 Driver Service — In-Memory State, Real-Time ✓ done

In-memory driver registry (map, no DB). Exposes gRPC RegisterDriver / UnregisterDriver. Consumes trip.event.created from RabbitMQ, picks a random matching driver by vehicle category, publishes triver.cmd.trip_request.

The design trade-off: No persistence = a restart loses all registered drivers. For this tutorial, simplicity wins. Production fix = Redis sorted set keyed by vehicle category.
CH09 Payment Service — Two-Interface Boundary ✓ done

Clean Architecture with two distinct boundaries: a domain-language Service interface and a provider-language PaymentProcessor interface. The service layer converts domain concepts (tripID, userID) to Stripe concepts (amount, currency, metadata). Listens on RabbitMQ, never exposes an HTTP or gRPC port.

The two-interface insight: Without the split, Stripe types leak into the service layer. Every caller would need to import the Stripe SDK. Swapping to PayPal = write one new PaymentProcessor struct, no other changes.
CH10 API Gateway — The System's Public Face ← you are here

Assembled the system's entry point in 6 files: json.go, middleware.go, types.go, http.go, ws.go, main.go. HTTP handlers proxy to gRPC. WebSocket handlers bridge RabbitMQ to browsers. Stripe webhook verifies HMAC before publishing.

5 key micro-decisions you implemented:
1. writeJSON — headers before WriteHeader (set after is a no-op)
2. io.ReadAll before JSON decode — Stripe HMAC needs exact raw bytes
3. json.RawMessage for driver responses — avoid decode/re-encode round-trip
4. Closure over rabbitmq in main.go — handlers testable, main owns wiring
5. defer cleanup on WS close — unregister driver on disconnect, not on timeout

Key Patterns

Reusable ideas beyond this project. Each one generalizes to other distributed systems.

01 AmqpMessage Envelope with OwnerID 
type AmqpMessage struct {
    OwnerID string `json:"ownerId"`  // routes to correct WebSocket
    Data    []byte `json:"data"`     // raw JSON, consumer unmarshals its own type
}
Why it matters Any system where you need to push async events to specific connected clients. The publisher doesn't know anything about WebSockets — it just sets a string. Generalize to: any fan-out system where you need per-recipient routing without the publisher knowing the recipients.
02 Event vs Command Routing Key Naming 
// <domain>.event.<verb>  → fact that happened, any number of consumers
// <domain>.cmd.<verb>    → instruction to a specific actor, usually one consumer

trip.event.created          // ← multiple consumers react
triver.cmd.trip_request     // ← directed at one driver
payment.cmd.create_session  // ← instruction to payment-service
Why it matters When debugging, you immediately know if a message is announcing vs instructing. Events enable open subscription; commands encode intent.
03 Centralized Idempotent Topology Declaration 
// Inside NewRabbitMQ() — every service calls this on connect
func setupExchangesAndQueues(r *RabbitMQ) error {
    r.Channel.ExchangeDeclare("trip", "topic", true, ...)
    r.Channel.QueueDeclare("find_available_drivers", true, ...)
    // ... all queues, all bindings
}
Why it matters AMQP declarations are idempotent. No "who creates the queue first?" race condition at startup. Any service can be the first to connect.
04 QoS Prefetch = 1 + Manual Ack 
r.Channel.Qos(1, 0, false)  // max 1 unacked message in-flight

// handler logic...

d.Ack(false)    // success → tell broker message is done
d.Reject(false) // failure → don't requeue → goes to DLQ
Why it matters Never auto-ack. Prefetch=1 + manual ack = fair dispatch across multiple instances + at-least-once delivery guarantee.
05 Dead Letter Queue with Enriched Headers 
// Before rejecting a failed message, add context:
d.Headers["x-death-reason"]       = err.Error()
d.Headers["x-origin-exchange"]    = d.Exchange
d.Headers["x-original-routing-key"] = d.RoutingKey
d.Headers["x-retry-count"]         = cfg.MaxRetries
d.Reject(false) // → routes to dlx → dead_letter_queue
Why it matters Makes debugging DLQ messages trivial — you know exactly why each message failed, where it came from, and how many times it was retried.
06 Single go.mod Monorepo 
// go.mod — one module, all services import shared code simply
module rebu

// Any service:
import "rebu/shared/messaging"
import "rebu/shared/contracts"
Why it matters No replace directives, no workspace file, no version mismatches between services and shared libraries. All services always compile against the same shared code.
07 Clean Architecture Dependency Direction 
// Dependency direction: infra → service → domain
// (arrows point inward, never outward)

domain/     ← pure Go structs, no imports from infra
service/    ← depends on interfaces (RepoInterface, PublisherInterface)
infra/      ← implements interfaces (MongoDB, RabbitMQ, Stripe)
Why it matters Swap MongoDB for Postgres or RabbitMQ for Kafka by changing only the infra/ layer. The service and domain layers never change.
08 Trace Propagation Through AMQP Headers 
// TracedPublisher injects traceparent into message headers
TracedPublisher(ctx, exchange, routingKey, msg, publishFn)

// TracedConsumer extracts it and starts a child span
TracedConsumer(delivery, handlerFn)

// Result: HTTP → gRPC → AMQP → gRPC → HTTP
// One trace ID covers the entire 30-step ride
Why it matters Jaeger shows the full ride as a single trace tree. Without this, each service's spans are isolated — you can't connect "payment-service received event" to "trip-service published it 200ms ago".
09 %w Error Wrapping for Inspectable Chains 
// %w (not %v) preserves the chain for errors.Is / errors.As
return fmt.Errorf("failed to connect: %w", err)

// Caller can distinguish transient from permanent:
if errors.Is(err, ErrInvalidAPIKey) {
    // permanent → skip retries → DLQ immediately
}
Why it matters With %v the error becomes an opaque string — no errors.Is. With %w the retry logic can make intelligent decisions: retry transient failures, dead-letter permanent ones.
10 Two Interfaces at the Payment Boundary 
// Service interface → domain language
type Service interface {
    CreateSession(tripID, userID, driverID string) error
}

// PaymentProcessor → provider language
type PaymentProcessor interface {
    CreateCheckoutSession(amount int64, currency string, meta map[string]string) (string, error)
}
Why it matters Without this split, Stripe types leak into business logic. Swapping to PayPal = write one new PaymentProcessor struct. The service layer and all consumers never change.
11 JSON Encoder vs Marshal — Decision Rule 
// Have an io.Writer (http.ResponseWriter, os.File)?
json.NewEncoder(w).Encode(data)   // streams, no temp []byte alloc

// Need []byte (store, sign, pass around)?
b, err := json.Marshal(data)

// Gotcha: Encode appends a trailing \n — fine for HTTP,
// matters if you're comparing exact byte output.
Why it matters Encoder streams directly into the writer — no intermediate allocation. For high-throughput HTTP handlers, this difference compounds.

Message Delivery Guarantees

📌

Persistent Delivery

DeliveryMode: amqp.Persistent — messages survive RabbitMQ restarts. Combined with durable queues.

🎛️

Prefetch = 1

RabbitMQ sends only 1 message per consumer at a time. Fair dispatch when multiple instances run. Next message only after explicit ack.

✋

Manual Ack

autoAck: false everywhere. d.Ack(false) on success. d.Reject(false) on failure → dead letter. No silent message loss.

🔁

Exponential Backoff

shared/retry retries the handler with backoff before rejecting. Only after all retries fail does the message go to DLQ.

Dead Letter Flow

handler fails after N retries
  → d.Reject(false)           // requeue=false
  → RabbitMQ sees x-dead-letter-exchange=dlx
  → message routed to dlx exchange
  → dead_letter_queue (bound to "#") catches it

The Quest — Test Your Understanding

10 questions drawn directly from the system. Click to reveal answers. No peeking!

Q1 The api-gateway uses var connManager = messaging.NewConnectionManager() as a package-level variable. You deploy two instances of the gateway behind a load balancer. Rider X is connected to instance A. A payment session message for rider X arrives at instance B. What happens? ▶

Instance B's QueueConsumer receives the message from RabbitMQ. It calls connMgr.SendMessage(riderX_ownerID, msg). Instance B's ConnectionManager has no entry for rider X — that connection is on instance A. The result: ErrConnectionNotFound and the message is dropped. Rider X never gets their payment link.

This is the sticky session problem. The production fix is Redis Pub/Sub: each gateway subscribes to a Redis channel keyed by userID. Any instance can publish to any user's channel regardless of where they're connected.

Q2 The Stripe webhook handler calls io.ReadAll(r.Body) before any JSON decoding. What specific error would Stripe's SDK return if you called json.NewDecoder(r.Body).Decode(&session) first, and then passed the body to the signature verifier? ▶

r.Body is an io.ReadCloser — it can only be read once. After Decode(), the body is fully consumed. A subsequent io.ReadAll(r.Body) returns []byte{} (empty).

webhook.ConstructEvent([]byte{}, signature, secret) computes an HMAC over empty bytes. This will never match Stripe's signature (computed over the full payload). The SDK returns: webhook signature mismatch.

The underlying rule: The signature is an HMAC of the exact raw bytes Stripe sent. Any transformation — JSON decode/re-encode can change whitespace, key ordering, float precision — invalidates the HMAC.

Q3 mux.Handle("POST /trip/preview", ...) uses Go 1.22+ method-scoped routing. What HTTP status does the mux return for GET /trip/preview? What about GET /nonexistent? Why does this matter? ▶

GET /trip/preview → 405 Method Not Allowed (with Allow: POST header). The mux knows the path exists but not for this method.

GET /nonexistent → 404 Not Found. No pattern matches at all.

This matters because pre-1.22 Go returned 404 for both — callers couldn't distinguish "wrong method" from "wrong path." With 1.22+, API clients and integration tests get meaningful status codes without needing a router library like gorilla/mux.

Q4 100 riders connect to the gateway simultaneously. Each rider's handleRidersWebSocket starts 3 queue consumers. How many goroutines are consuming from notify_payment_session_created? What architectural problem does this cause? ▶

100 goroutines consuming from that single queue (one per rider for that queue). Total across all 3 queues: 300 goroutines.

RabbitMQ delivers each message to exactly one consumer (round-robin with Qos=1). If rider X's payment message is delivered to the goroutine started by rider Y's connection, the consumer reads OwnerID = X and correctly routes it via connMgr.SendMessage to X's connection. Correctness is maintained, but 100 open AMQP consumers for one queue is wasteful.

The architectural fix: One shared QueueConsumer per queue per process (started at startup, not per-connection). It acts as a dispatcher — receives all messages, routes each to the correct WebSocket via connMgr.SendMessage(ownerID, msg).

Q5 The driver WebSocket handler uses json.RawMessage for the Data field when forwarding driver accept/decline to RabbitMQ. Why not map[string]interface{}? What could go wrong with the simpler approach? ▶

With map[string]interface{}: deserialise the incoming JSON to a map, then re-serialise it to pass to RabbitMQ. This round-trip can alter the byte representation: different key ordering (Go maps don't preserve order), different float precision, added/removed whitespace.

json.RawMessage preserves the exact bytes from the WebSocket message. No parse, no re-encode. The trip-service receives exactly what the driver's browser sent. Also faster — no two alloc cycles.

Generalisation: When you're acting as a passthrough (receive bytes → forward bytes), avoid deserialise/re-serialise unless you need to inspect or transform the content.

Q6 The driver-service stores driver state in an in-memory map. What happens on a pod restart in Kubernetes? What would you use in production and why? ▶

All registered drivers are lost. Drivers already at their vehicles with the app open would need to re-connect and re-register to be visible for new trips. Any pending trip matching would find zero available drivers until drivers reconnect.

Production fix: Redis. Specifically, a Redis sorted set (or hash set) per vehicle category, keyed by driverID. Redis survives pod restarts, can be shared across multiple driver-service instances (solving the horizontal scaling problem), and supports atomic operations like SRANDMEMBER for random driver selection.

Q7 What is the difference between fmt.Errorf("msg: %w", err) and fmt.Errorf("msg: %v", err)? Give a concrete example of when the difference matters in this codebase. ▶

%v converts the error to a string — the chain is severed. %w wraps the error, preserving the chain so errors.Is(err, targetErr) and errors.As(err, &target) can inspect the root cause.

Concrete case in this codebase: The RabbitMQ consumer's retry logic. If Stripe returns ErrInvalidAPIKey (permanent failure), the consumer should dead-letter immediately without retrying — retrying a bad API key 3 times is wasted work. With %w, the retry loop can call errors.Is(err, ErrInvalidAPIKey) and skip straight to DLQ. With %v, it's an opaque string — the retry logic can't distinguish transient from permanent.

Q8 The routing key for driver commands is triver.cmd.trip_request (note: triver, not driver). You add a second consumer of these events in a new service and use driver.cmd.trip_request as the binding. What happens? ▶

Your queue binding key is driver.cmd.trip_request. The publisher emits triver.cmd.trip_request. RabbitMQ topic exchange does an exact match on routing key words — triver ≠ driver. Your queue receives zero messages. No error, no warning — silent non-delivery.

This is documented in the vault notes as an open question. The typo is in shared/contracts/amqp.go as a constant. As long as you use the constant rather than hardcoding strings, you'll use the correct (typo'd) value automatically.

Lesson: Always use the shared constants, never raw strings. Let the compiler catch the mismatch.

Q9 Explain the Clean Architecture dependency direction in this codebase. Which layer can import which? Give the concrete example from payment-service. ▶

Direction: infra → service → domain. Arrows point inward. Domain never imports anything except the standard library. Service depends on interfaces. Infra implements those interfaces.

Payment-service concrete example:

• domain/ — defines PaymentEvent struct (pure Go, no imports)

• service/ — defines PaymentProcessor interface (provider-agnostic) and Service interface (domain-language). Depends on those interfaces only.

• infrastructure/stripe/ — implements PaymentProcessor with the Stripe SDK. Imports Stripe. The service layer never imports Stripe.

Result: Replace infrastructure/stripe/stripe.go with infrastructure/paypal/paypal.go that implements the same PaymentProcessor interface. Zero changes to service/ or domain/.

Q10 The writeJSON helper sets the Content-Type header before calling w.WriteHeader(status). What happens if you swap the order — call WriteHeader first, then set the header? ▶

In Go's net/http, calling WriteHeader (or implicitly writing the body) locks the headers. Any w.Header().Set() call after WriteHeader is a no-op — the headers have already been sent to the client.

Concrete result: The response arrives with no Content-Type header (or with the Go default text/plain; charset=utf-8). Browsers and API clients that rely on Content-Type: application/json to decide how to parse the response may fail or show raw text.

Go logs a warning: "superfluous response.WriteHeader call" if you call WriteHeader twice, but silently ignores header changes after the first WriteHeader. Hard to debug without knowing this rule.
